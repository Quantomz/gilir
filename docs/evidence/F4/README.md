# F4 evidence

Card F4 lets a farmer reopen saved answers and a saved result on the same device, with no account, and download a PDF that opens offline. Everything in this folder is **fixture evidence**. The snapshots are synthetic, built from `src/fixtures/` and `tests/frontend/pdf/support/variants.ts`, and every PDF page carries the synthetic label. No live backend ran. **Live end-to-end evidence was not run here.** Cards I1 to I3 gate the assembled application.

The browser checks ran in Chromium (Google Chrome for Testing 153.0.8010.12, headless) on the F4 harness. The harness serves the real `src/client/storage.ts` and `src/client/pdf.ts` through Vite, which comes in through `vitest/node` and is not a direct dependency. No F1 or F3 page was involved. Every command ran with Node 24 (`PATH=/opt/node24/bin:$PATH`).

## What each card item rests on

**A saved result stays readable after a browser restart and a server expiry, and draft and job restoration are covered.** `storage.spec` saves a partial draft, page 3, a job capability and the plan snapshot, closes Chromium, launches it again on the same user data folder, and loads the same state with the snapshot's id, date and provenance unchanged. With every `/api` request answering 404 `not_found`, and again with every request failing, a reload still loads the snapshot. The route sees only the test's own probe request, so `load` sent nothing. `load`, `save`, `readStorageNotice` and `clear` send no request at all.

Snapshots of both contract versions are kept. Version 1 has no catalogue; version 2 carries the crop catalogue frozen when the plan completed. All six fixture states of each round trip through `localPlans` unchanged (`record.test.ts`), and a raw record holding either version restores after a reload in Chromium (`storage.spec`). Storage validates them with the shared `completedSnapshotSchema` and the active job with the shared `jobCapabilitySchema`, and declares no schema of its own.

**A full device, blocked storage and an invalid old record give useful words, with no silent loss and no made-up defaults.** With a 256 KB quota, a save of incompressible data rejects with "This device has no room left to save Gilir.", the earlier state still loads, and a save that fits still works. In a sandboxed frame, `load`, `save` and `clear` reject with "This browser isn’t letting Gilir open or save your answers on this device." An old record written with raw IndexedDB loads its answers with the snapshot left out (null, never a default), the notice says "Your saved plan can’t be opened by this version of Gilir. Make the plan again to see it. Your answers are kept.", and the record sits unchanged in the set-aside record. A notice read in the same tick as that load, before it or after it, names the plan too, and after a dismiss it doesn't come back. The notice survives a restart until dismissed and stays gone after a dismiss and a restart. Clearing site data while the page is open makes the next load resolve null, not reject. A newer database rejects "newer" and stays untouched. Every record, the state and the set-aside one, carries the FarmInput, CompletedSnapshot and RunManifest versions of the build that wrote it. So an older build refuses a newer build's records, or a snapshot whose input or run manifest is newer, instead of setting them aside or deleting them (`record.test.ts`). On a full device, a load that can't set an unreadable part aside still returns the readable answers, the notice still names that part, and the next save sets it aside first or rejects "full" with the old record kept. `record.test.ts` shows it with the IndexedDB double, where only QuotaExceededError lets load skip that write: UnknownError rejects "unavailable" and AbortError is retried. `storage.spec` shows the load in Chromium. It sets a 512 KB quota, writes a record holding an unreadable plan, and fills a second database until a write fails with QuotaExceededError. The load then returns the answers and writes nothing, the notice names the plan, and clear still works. That test passed 20 of 20 runs before it was committed. An earlier probe that only lowered the quota made the write fail now and then, which is why the test fills the origin instead. Another tab's upgrade is not blocked. A tab holding the database stops a save at the 5 s limit, and that save changed nothing. The farmer sees these words only once F1 shows them, so the screen half of this item is PARTIAL.

**The fixture lab never touches the farmer's database.** A save under `/dev/fixtures/` is invisible at `/` and the reverse, `indexedDB.databases()` lists `gilir` and `gilir-fixture-lab`, and Clear in the lab leaves the farmer's state.

**A PDF names each crop by the label saved with the result.** `cropName` in `src/client/pdf/text.ts` decides every crop name from the snapshot: the answers line, the status sentence, flags and warnings, the calendar rows, heat and cold, the changes from last year, the duration proof, What’s missing, the unassessed checks, last year’s rows and the crop profiles. A version 2 snapshot prints its frozen label, made printable, with its own capitals ("Brussels sprouts"). A version 1 snapshot, a crop its frozen catalogue lacks, and a label with a letter the fonts can’t draw print the name made from the ID, such as "Synthetic old crop", never a "?"; inside a sentence it is lower case. A crop list that holds a name with "and" or a comma in it is split by semicolons ("Pumpkin and winter squash; Squash and zucchini"). The registry's own reason for a gap names the crop by its ID ("No released common-bean-dry profile applies at this location."), so the PDF puts the crop's name in place of each of the gap's own IDs that stands alone. An ID inside a longer one, such as a profile ID, is left as it is, and the "Crop profiles:" source line still lists each profile ID next to the crop's name. A date that is part of an ID, such as catalogue fao56-hard-windows-2026-11-15, is no longer rewritten as a date. `compose.test.ts` takes real gaps from `resolveRegistry` and real proofs from `findCalendar`. `compose.test.ts` and `export.test.ts` check each case, the export ones on the text read back from the PDF. [inspection.md](inspection.md) records the six pages of `variant-frozenLabels.pdf` and the version 2 status reports looked at in scratch.

**Each sentence is true of the result it prints.** A no-fit report from a duration proof asks for crops that grow faster, and for fewer crops only when more than one was chosen. A structural proof comes only after the crops' days fit in the year, so the hard planting windows, or the follow rules when the run had any, stopped them. The report says so with the start date, and suggests another start date or other crops, and fewer crops when there are several. It names no date that would work. One rice crop at Bangkok from 15 Jan 2027 gives "The time of year when your crop can be planted leaves no way to fit it into one year from your start date, 15 Jan 2027." A no-plan report whose last-year rotation was scored lists that rotation's numbers in past seasons and the rows the farmer gave, instead of "No numbers to compare." A no-plan report says "Weather from 25 past seasons", never "Checked against", since nothing was checked. Every crop profile note is headed "About the growing details for <crop>", because most notes say which FAO-56 row was read, not what the water check leaves out.

**PDFs from a plan, a warning plan and the missing-data fixture open offline and were inspected.** Each downloads as `gilir-plan-2026-07-01.pdf`, starts with `%PDF-`, equals the node render byte for byte, and opens in Chromium's PDF viewer with the network off, which shows its title and page count. [inspection.md](inspection.md) records every page. After `preparePdf`, a download works with the network off. Once the PDF code has loaded, making all six files sends no request. With storage denied, `exportPdf` still returns a PDF.

## Not run or not shown here

- **NOT RUN.** Live end-to-end evidence with the assembled application and a real backend. Cards I1 to I3 own it.
- **NOT RUN.** Safari and Firefox. Every browser case ran in Chromium only.
- **NOT RUN.** A real cheap phone. The 6x throttle slows only the page's main thread, not IndexedDB's disk work.
- **Not shown.** The registry's "can be confirmed" and "Ambiguous profile precedence" gap reasons from the real engine. The current release gives neither at Bangkok, and its validation rejects ambiguous precedence. `compose.test.ts` writes the ambiguous one as the registry would; the other is not tested. Real engine runs exist only for Bangkok and Pretoria weather.
- **NOT RUN.** The specs under the root `playwright.config.ts`. Its web server starts `next dev`. Both configs list the same 24 cases.
- **Not kept here.** The PDFs of the other three result states, the other 14 variants and the Letter plan. The layout and export tests render every one of them on A4 and Letter; `evidence.ts --all` writes them for a person to look at.
- **PARTIAL.** The farmer seeing the storage words and the set-aside notice. That needs F1 to show `readStorageNotice()` and `storageProblem(error).text`.
- **Not shown by the harness.** Retrying the PDF after an offline failure. `export.test.ts` covers it in Vitest: the render import fails once, and the next export returns a PDF. Without the reset in `pdf.ts` that test fails. The harness can't show it in Chromium, because it loads native ES modules and Chromium keeps a failed module fetch. The product build loads the PDF code as a webpack chunk, which forgets a failed load. A one-off production build with a probe page (outside the repo, then deleted) showed an offline export reject twice and the next online export return a PDF, in 3 of 3 rounds.
